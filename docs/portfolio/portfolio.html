결제 · 환불 정책 개선과 우편 발송 자동화

편지 인쇄 · 우편 발송 플랫폼 — 결제수단 분리와 환불 정책 확장

토스페이먼츠 카카오페이 NestJS
문제
적립금을 100% 사용한 주문도 PG 결제창을 거쳐 0원 결제가 발생했고, 결제 후 오래된 주문은 PG 자동 취소 기한(카드 364일, 계좌이체 · 간편결제 179일)을 넘겨 환불이 실패할 수 있었습니다. 예약 발송 건의 인쇄 수거와 우체국 추적 조회도 수동 작업이었습니다.
설계 · 구현
적립금 전액 결제를 PG를 거치지 않는 자체 결제수단으로 분리하고 기존 주문을 마이그레이션으로 백필했습니다. 환불 정책 계산에 PG 취소 기한을 넣어 기한 경과 건은 DB 커밋 전 409로 선차단하고 마이페이지에서 계좌 환불 경로를 안내했으며, 약관 제10조와 운영 문서를 갱신하고 테스트를 추가했습니다. 예약 해제분 자동 인쇄 수거와 우체국 XML 응답 파싱, 추적 조회 1일 2회 스케줄을 구현했습니다.
결과 · 역량
결제수단과 환불 정책을 안전하게 확장해 0원 PG 결제와 환불 실패 민원을 제거했고, 우편 발송의 수동 작업을 없앴습니다. 다른 서비스의 PG(포트원) 사전 점검 지적도 공개 사업자 정보 페이지 추가로 당일 해소했습니다.

UUID 기반 파일 식별

업로드와 Drag & Drop 재정렬에서 순서가 바뀌어도 같은 파일을 안정적으로 추적

초기 접근 — useRef 카운터

  • !ID 충돌 가능성파일 / 폴더 업로드 탭이 독립적으로 ID를 생성하면 상위 병합 시 key 충돌
  • !컴포넌트 결합도 증가부모에서 ID를 생성하도록 강제하면 하위가 부모 로직에 의존

최종 선택 — crypto.randomUUID()

  • 01전역 고유 ID 보장파일이 어느 컴포넌트에서 생성되든 충돌 없음
  • 02index 무관 추적D&D 시 렌더링 index 변화와 무관하게 동일 파일 추적
  • 03컴포넌트 독립성 유지별도 충돌 방지 로직 불필요, 이후 기능 확장에도 유리

EXIF 방향 문제와 Canvas 정규화 파이프라인

화면 표시가 아니라 픽셀 데이터 자체를 정상 방향으로 재생성

초기 접근 — ArrayBuffer 직접 삽입

  • !현상ArrayBuffer를 그대로 PDF에 삽입하면 EXIF 방향 보정이 반영되지 않음
  • !구조적 원인pdf-lib 변환 과정에서 EXIF 메타데이터 기반 방향 정보가 유지되지 않음
  • !리스크동일 파일도 기기 · 브라우저에 따라 다른 방향으로 출력

EXIF 미반영 → 출력 방향 오류

해결 — createImageBitmap + Canvas

  • 01createImageBitmap(file)EXIF가 반영된 비트맵을 생성해 방향 차이 흡수
  • 02Canvas 재드로우재렌더링으로 픽셀 방향 고정
  • 03JPEG 재인코딩정규화 이미지로 재인코딩 후 PDF 삽입
  • 04ArrayBuffer Fallback정규화 실패 환경에서도 변환이 중단되지 않도록 대비
